# Clinical SDTM Artifacts

Use `workbench_get_use_case("sdtm")` as the current contract. This workflow requires EDC JSON/XLSX. A blank CRF PDF is optional: include it to generate and review an aCRF, or omit it for mapping, Define-XML, and R/SAS code generation without an aCRF. Submission normally uses the web UI or multipart REST API rather than the text-only MCP submission tool.

Before SDTM mapping, an intake agent normalizes the deterministically extracted JSON/XLSX into an `EDCSourceSpecification`. The job pauses in `review_required` until a user reviews dataset/variable identifiers, types, keys, codelists, form/question links, and file/sheet/row provenance and approves the complete source schema.

After intake approval, the SDTM workflow runs three ordered stages:

1. Domain mapping determines each raw or existing SDTM source-dataset to target-SDTM-domain relationship as direct, stack, join, split, or derived. Stack appends source observations as rows; join adds columns using reviewed keys and cardinality. Do not use an ambiguous merge category.
2. Variable mapping runs isolated, bounded-parallel agents per target domain to determine complete multi-source traceability, value-level metadata, and minor per-variable derivations; its deterministically ordered combined result requires one human approval. It does not own record construction or executable expressions. CDISC reference responses omit repeated navigation links while retaining complete metadata, and transient model-service failures retry only the affected domain without rerunning accepted domains. When a blank CRF is supplied, its CRF source labels drive the aCRF annotations.
3. Rule/code augmentation likewise runs bounded-parallel agents per target domain and adds one ordered typed record-construction plan plus one implementation rule per target variable before one combined approval. Filter steps contain executable reviewed R and SAS boolean conditions, not prose, and are validated here. Record preparation is not free-form model code: the backend compiles the approved read/stack/join/transpose/filter/deduplicate/aggregate plan deterministically into each domain program.

After the ordered specialists finish, the registered SDTM lead rereads the user-approved EDC source specification and any supplied blank CRF and reconciles all three drafts under `backend/app/agents/sdtm/mapping_policy.md`. Treat stage drafts as fallible observations; only the lead's complete, cross-stage-validated `SDTMPlan` proceeds to deterministic rendering.

- Query CDISC Library MCP tools for the exact SDTMIG product, domains, variables, and controlled terminology needed. Preserve returned version identifiers.
- Poll the workbench job, complete the EDC source review gate when requested, and then review all three mapping stages, source-to-target traceability, origins, keys, derivations, value-level metadata, unresolved mappings, Define-XML references, and rule-to-code consistency. Review aCRF annotations only when a blank CRF was supplied.
- In the web review editor, use the ordered Domain mapping, Variable & VLM, Rule & code, aCRF review, and Define-XML tabs. Use drag-and-drop for raw-to-SDTM or SDTM-to-SDTM domain mappings and import versioned CDISC dataset metadata when needed. Use the variable-by-source matrix to inspect direct, stacked, joined, and value-level source slices; select a row or cell to edit target metadata, minor derivation, detailed lineage, and VLM rows. Each current base or VLM source reference can be removed directly from its matrix cell; this removes only that reference and leaves other sources and VLM metadata intact. Show stage-wide feedback decisions above the domain selector and present both stage-wide and domain-specific assumptions and unresolved constraints through the same read-only feedback-decision panels with their audit context; do not duplicate them in comment textareas. Add or remove shared VLM columns at matrix level and keep wide-to-long findings aligned by one normalized test-code condition across code, name, result, unit, standard-result, range, and flag cells. Pending Variable/VLM patches appear as overlays in that same matrix: proposed-only columns are marked and changed cells show current and proposed lineage and logic together, while proposed references remain read-only and approval remains a separate transaction-level human decision. Rule & code presents the exact generated per-domain R and SAS artifacts as read-only syntax-highlighted source with download access; revise mappings or rerun the domain to rebuild them. Treat sponsor SUPP additions as editable draft metadata. The aCRF and Define-XML tabs are derived previews; revise their source metadata in the mapping tabs and rebuild.
- In a completed job, Variable & VLM and Rule augmentation are reviewed and rerun per target domain. A Variable & VLM rerun must also regenerate the selected domain's dependent rules. Keep the approved result and artifacts active while the proposal is generated, show the exact domain-scoped patch, and require human approval before deterministic artifact replacement. Preserve every untouched domain. After approval, mark execution and validation `not_run` for the new programs and retain prior evidence as historical only; rejection leaves the approved package unchanged.
- Generated R may run only through the isolated Workbench runner after raw datasets are supplied and a human initiates execution. Never execute SAS and never claim regulatory conformance.
- For user-approved mapping changes, send the complete revised structured result to `workbench_update_job_result`. The API revalidates and rebuilds mappings, Define-XML, optional aCRF, program scaffolds, manifest, and ZIP without another model call.

Keep SDTMIG 3.4 / Define-XML 2.1 outputs labeled as draft metadata.
