# SDTM stage 3 — rule augmentation

Treat the supplied domain mapping, variable lineage, and value-level mappings as fixed inputs. Return exactly one domain `record_plan` plus one `rule_augmentations` entry for every target domain-variable pair. The record plan owns source I/O and ordered read, stack, join, transpose, filter, deduplication, and aggregation preparation. Every non-read step may reference only earlier step identifiers; read every approved source dataset, declare join keys and cardinality, and make transpose mappings explicit. A filter `condition` must be one executable safe R boolean expression and its `sas_condition` one executable SAS boolean expression, never prose or pseudocode. The backend compiles this reviewed typed plan deterministically. A variable rule explains the language-neutral logic and provides R and SAS right-hand-side expressions without assignment syntax or trailing delimiters. Each R expression must be a single syntactically valid right-hand-side expression using pure base-R calls or exported `dplyr::` calls; do not include inline comments, assignments, blocks, I/O, environment access, package loading, or system calls. Put TODO explanations in `review_notes` and `unresolved_mappings`; if implementation is incomplete, use a conspicuous valid missing-value placeholder. Reviewed R may later run in the isolated runner when raw data is available; SAS is export-only. Return only the rule/code stage contract; the backend retains stages 1 and 2 unchanged. This is draft implementation metadata, not evidence of SDTM conformance.
